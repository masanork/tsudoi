# tsudoi 仕様書（初版）

## 1. プロダクト概要

**tsudoi** は、イベント・会場ごとの参加者名簿、事前申込、当日受付を一元管理する軽量 SaaS である。主催者は参加状況を即時に把握でき、参加者は Passkey またはメールの安全なリンクを使って、自身の QR チケットの確認・キャンセル・主催者との連絡を行える。

### 成功条件

- 会場スタッフが QR の提示または検索だけで、参加可否を素早く確定できる。
- 同一チケットを複数回受付にしない。オフライン時の扱いは明示して後続フェーズで追加する。
- 参加者本人以外がチケット、キャンセル画面、メッセージ本文にアクセスできない。
- 主催者・参加者間のメッセージ本文はサービス運営者を含む第三者が復号できない。
- 主催者が API とダッシュボード双方で、申込数・受付数・取消数を同じ定義で確認できる。

## 2. 用語とテナント境界

| 用語 | 意味 |
| --- | --- |
| 組織 | 主催者アカウントのテナント。請求、メンバー、データ隔離の単位。 |
| 主催者 | 組織内でイベントを運営するユーザー。`owner` / `admin` / `staff` / `viewer` のロールを持つ。 |
| イベント | 申込・チケット・通知・集計の親。公開日時、定員、申込方式を持つ。 |
| 会場 | 受付を実施する物理的またはオンラインの場所。1 イベントには複数設定できる。 |
| 参加者 | 申込者。個人単位で一意のチケットを持つ。 |
| チケット | QR を含む入場資格。状態は参加者ではなくチケットに保持する。 |
| 受付 | スタッフがチケットを検証して来場を記録する操作。 |

すべての業務データは `organization_id` を持つ。組織を跨ぐ URL 推測、API リクエスト、キャッシュ混入を防ぐため、認可判定は常にテナント条件を含める。

## 3. 利用者と権限

| 利用者 | 主な操作 |
| --- | --- |
| 組織 owner | 請求、組織設定、主催者管理、全イベントの管理。 |
| admin | イベント作成・公開、スタッフ管理、メッセージ閲覧用の暗号鍵を管理。 |
| staff | 割り当て会場の受付、名簿の限定閲覧、参加者への連絡。返金・組織設定は不可。 |
| viewer | 集計・名簿の閲覧のみ。個人情報のエクスポートは禁止を既定とする。 |
| 参加者 | 申込、チケット表示、本人のキャンセル、E2EE メッセージ、通知設定。 |

主催者は mikaki の OIDC で本人認証する。スタッフ権限はイベント・会場単位に制限可能とする。

## 4. 機能要件（MVP）

### 4.1 イベント・会場・名簿

- 主催者はイベント名、説明、開始・終了日時、タイムゾーン、公開状態、定員、申込期間を設定できる。
- 会場は名称、住所、受付時間、受付レーン（任意）、定員（任意）を持つ。
- 名簿はイベントごとに表示し、会場・状態・申込経路・検索語で絞り込める。
- 参加者の標準項目は氏名、表示名、メールアドレス（任意）、所属（任意）、申込時のカスタム回答とする。カスタム項目は型、必須、公開範囲を定義できる。
- 主催者はカスタム項目を後から追加し、名簿では表示カラムの追加・順序変更・非表示を行える。項目は安定した ID で管理し、変更・廃止しても既存回答を失わない。廃止は物理削除でなく新規申請から隠す操作とする。
- 名簿の CSV エクスポートは `admin` 以上に限定し、実行者・対象イベント・項目・時刻を監査ログへ残す。

### 4.2 申込・チケット

- イベントごとに次のいずれかを選ぶ。
  - **事前申込**: 公開フォームから登録。定員に達した場合は締切、または待機列へ遷移。
  - **当日受付**: スタッフが参加者を検索・新規登録して即時チケットを発行。
  - **併用**: 事前申込者と walk-in を同一名簿で扱う。
- 個人ごとに推測不能なチケット ID を発行し、QR には個人情報を入れない。QR は短命または失効可能な署名付き検証トークンを表す。
- チケット状態は `issued`、`cancelled`、`checked_in`、`voided`。状態遷移は監査可能にする。
- 受付時はスタッフが QR を読み取り、サーバーで有効性・会場・状態を原子的に確認して `checked_in` にする。重複読取には最初の受付日時と担当を表示し、再受付には明示権限を求める。
- 手入力のチケット検索・受付を提供する。誤操作の取消は権限付きで理由を記録する。

### 4.3 参加者の本人確認とセルフサービス

- Passkey: 参加者は最初の申込後またはチケット画面で Passkey を登録し、以後その Passkey でログインできる。
- メール: メールアドレスを登録した場合、QR 付きチケットを送付する。メール内のリンクは一度限り・短時間有効な本人確認リンクとし、リンクを開いた端末ではチケット確認、Passkey 登録、キャンセルを可能にする。
- メール未登録の参加者には、申込完了画面で QR 保存と Passkey 登録を強く案内する。チケットを失った場合の再発行は、主催者による本人確認フローを必要とする。
- キャンセル可否・期限・キャンセル待ち繰上げの有無はイベントごとに設定する。キャンセル後の QR は即時無効化する。
- 認証リンクを転送された場合のリスクを低減するため、重要操作（メール変更、Passkey 追加、個人情報全件表示）には Passkey またはメール再認証を要求する。

### 4.4 E2EE メッセージ

- 参加者とイベント運営窓口の間に 1 対 1 のスレッドを提供する。メッセージ本文、添付ファイル本文、添付ファイル名はクライアント側で暗号化してから送信する。
- サーバーが保持するのは暗号文、暗号方式バージョン、宛先キー ID、配送状態、最小限の時刻・スレッド識別子のみとする。本文検索、サーバー側モデレーション、本文を含むプッシュ通知は提供しない。
- PRF 対応 Passkey では、WebAuthn PRF 出力から導出した鍵暗号化鍵で端末鍵・復旧鍵を保護する。PRF の出力、復号鍵、平文秘密鍵はサーバーへ送らない。PRF 非対応または Passkey 非対応の場合は、端末で鍵ペアを生成し、利用者が保管する回復コードからクライアント側で導出した鍵でバックアップを暗号化する。メールリンクは本人認証と暗号化済みバックアップの取得だけに用い、単独では復号できない。旧端末と回復コードをともに失ったときは新しい鍵を作るが、過去本文は復号できないことを UI 上で明示する。
- 主催者側は、イベント窓口用の暗号鍵をロールに応じて各主催者デバイスへラップして配布する。スタッフを外したときは新しい鍵世代にローテーションし、以後のメッセージを旧スタッフが復号できないようにする。過去分の再暗号化可否は将来要件とする。
- 添付は暗号化バイト列を R2 に置き、短期署名 URL ではなく認可済み Worker 経由で配布する。

### 4.5 通知

- Web Push を、参加者の明示的な許可とイベント単位の購読設定に基づき配信する。
- 通知種別は `message_received`、`event_updated`、`ticket_updated`、`reminder`。メッセージ通知は「新しいメッセージがあります」等の本文を含まない文面にする。
- 配信対象の抽出、再試行、期限切れ subscription の削除は非同期化する。メール送信も同じく非同期とする。

### 4.6 ダッシュボードと API

- ダッシュボードは mikaki OIDC の検証後に tsudoi が発行する `HttpOnly`・`Secure`・`SameSite=Lax` セッションで認証する。ブラウザへ API トークンや組織 ID を保存・表示・入力させない。
- API トークンはダッシュボードのログイン手段ではなく外部連携専用とする。発行時のみ平文を表示してコピー可能とし、以後はラベル、スコープ、有効期限、失効、ローテーション、監査ログを管理する。
- 参加者がいない下書きイベントだけは、確認操作を経て関連する日程候補・フォーム・会場設定とともに完全削除できる。公開済みまたは参加者のいるイベントは受付を停止してアーカイブし、通常の一覧と公開ページから隠しつつ記録と監査ログを保持する。
- ダッシュボードはイベント・会場・申込経路ごとに、`申込数`、`発券数`、`取消数`、`受付済数`、`未受付数`、`定員充足率` を表示する。
- 数値定義: 申込数は有効な参加者レコード、発券数は `issued` または `checked_in`、取消数は `cancelled`、受付済数は `checked_in`、未受付数は `issued` とする。期間・タイムゾーンを画面/API で明示する。
- API は組織スコープの OAuth または発行済み API トークンで保護し、読み取り専用・名簿読み取り・受付書き込み・管理のスコープを分ける。
- 最初の公開 API: `GET /v1/events`、`GET /v1/events/{id}/metrics`、`GET /v1/events/{id}/attendees`、`POST /v1/tickets/{id}/check-in`。ページネーション、冪等キー、監査ログを必須とする。

## 5. 非機能・セキュリティ要件

- 日本語を初期言語とし、モバイル受付で片手操作できる UI、キーボード操作、十分な色コントラストを提供する。
- PII、QR トークン、メールリンクをアクセスログや分析イベントに出力しない。保存時暗号化、転送時 TLS、秘密情報のシークレット管理を行う。
- 申込、メールリンク発行、QR 検証、メッセージ送信、API を IP・アカウント・イベント単位でレート制限し、公開フォームには Turnstile を適用する。
- 監査対象: 権限変更、名簿閲覧・出力、参加者情報変更、状態変更、チケット検証、API トークン操作、暗号鍵世代変更。
- 保持期間をテナントごとに設定できるようにする。削除要求では PII を匿名化し、会計・監査上必要な最小イベントを期限付きで残す。E2EE 暗号文の削除も同時に行う。
- 可用性目標、RPO/RTO、障害時受付運用、法令・プライバシーポリシー、決済は MVP の前提外として別途確定する。

## 6. 推奨アーキテクチャ

```text
Svelte PWA ── HTTPS ──> Worker (Hono: UI API / auth / QR verification)
                              │       │          │
                              │       │          └── WebAuthn / Web Crypto (client-led E2EE)
                              │       ├── D1: tenancy, roster, tickets, audit, ciphertext metadata
                              │       ├── R2: encrypted attachments, ticket assets
                              │       ├── KV: rate limits, short-lived auth state/cache
                              │       ├── Queues: email + Web Push fan-out/retry
                              │       └── Analytics Engine: aggregate operational events
                              │
                              └── repository interfaces ──> D1 now / Hyperdrive + external DB later
```

参考する `tossa` と同様に、Workers + Hono、Svelte 5 + Vite、WebAuthn、Web Push、D1、R2、Queues を基本構成とする。メールは Cloudflare Email Sending または交換可能な `EmailProvider` 実装で送る。

### データ分離と将来の外部 DB

- アプリ層は `RosterRepository`、`TicketRepository`、`MetricsRepository`、`MessageRepository`、`AuditRepository` のインターフェースだけに依存し、D1 の SQL を HTTP ハンドラへ書かない。
- D1 はトランザクション整合性が必要なテナント、イベント、名簿、受付、監査の初期ストアとする。`check_in` は単一の原子的なユースケースに閉じる。
- `DataStore` 実装を D1 と外部 Postgres/MySQL 用に分ける。外部 DB 接続時は Hyperdrive を経由し、スキーマ・ID・タイムゾーン・監査イベント形式を共通に保つ。
- 非同期イベントは `ticket.checked_in` 等のバージョン付き outbox として保存してから Queue へ渡す。これにより通知・集計・外部同期を DB 実装から切り離す。
- E2EE の暗号文・鍵包み・R2 オブジェクト参照は DB に依存しないフォーマットにし、移行時にも暗号文を復号・再暗号化しない。

## 7. 概念データモデル

| エンティティ | 主な属性 |
| --- | --- |
| organizations / organization_members | 組織、ロール、状態 |
| events / venues | 公開設定、日時、定員、受付・キャンセル設定、会場 |
| attendees | イベント・会場、PII、申込経路、同意、状態 |
| tickets / check_ins | チケット ID、トークン鍵 ID、状態、受付担当・時刻・端末 |
| passkeys / magic_links / sessions | WebAuthn credential、リンクハッシュ・期限・消費時刻、セッション |
| message_threads / encrypted_messages / key_envelopes | 当事者、暗号文、鍵世代・宛先キー、配送状態 |
| push_subscriptions / notification_jobs | 購読情報、通知種別、配送結果 |
| event_metrics / audit_logs / outbox_events | 集計スナップショット、監査、非同期連携イベント |

メールアドレスと magic link の生トークンは保存しない。メールアドレスは検索要件を満たす方式で正規化・暗号化し、リンクはハッシュのみ保存する。

## 8. 画面と主要フロー

1. 主催者: mikaki でログイン → 初回のみ組織・管理者作成 → イベント・会場・フォーム公開 → ダッシュボードで状況確認。
2. 事前申込者: 申込 → チケット発行 → メール受信（任意）/ Passkey 登録 → QR 表示 → 来場・受付 → 必要に応じて E2EE 連絡またはキャンセル。
3. 当日受付: スタッフが Passkey ログイン → 会場を選択 → QR 読取または検索 → 一度だけ受付確定 → 成否を大きく表示。
4. 更新通知: 主催者がイベントを更新 → outbox → Queue → 購読者へ本文非含有の Push → アプリで本人認証後に詳細表示。

## 9. MVP の受入条件

- 事前申込・当日受付・併用の各イベントで、チケット発行から QR 受付までを完走できる。
- 同じ QR を同時に 2 回送信しても、受付成功は 1 回のみである。
- メール登録者は受信リンクからチケット表示と設定された条件内のキャンセルができる。
- Passkey 登録者は別セッションでも本人のチケットを閲覧できる。
- 権限のない組織・スタッフ・API トークンは、他組織または非担当会場の名簿・受付にアクセスできない。
- E2EE メッセージの DB/R2 保存物だけから、本文・添付名を読めない。
- ダッシュボード数値と API 数値が同じイベント・フィルター・時点で一致する。

## 10. MVP 後に決める事項

- 複数人申込、同伴者、座席、チェックポイント複数回通過、QR の完全オフライン検証。
- 有料チケット・返金・インボイス、待機列の自動繰上げ。
- メールを持たない参加者の厳格な回復手段、E2EE 鍵の組織的エスクローを許すかどうか。
- 外部 DB 移行の契機（容量、分析要件、リージョン要件）と対象（読み取りレプリカのみか一次ストアも含むか）。
- 管理者による不正利用対策と、E2EE のゼロ知識性を損なわない通報・同意フロー。
