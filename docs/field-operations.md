# 平時のイベント運営と避難所での利用に向けた拡張

ユーザー依頼に基づき、司令塔・API実装者・UI実装者・独立レビュワーで、配布管理、入退館履歴、紙のQRカード・世帯管理、通信断対応の順に実装する。既存の登録・単発受付・参加者認証・メールを維持し、同じイベント内の発行済み受付QRを各用途で利用する。

## 1. 配布管理

- 管理者が「昼食」「夕食」「ノベルティー」などの配布回を後から追加する。回ごとに名称、単位、1人あたり上限、実施中/停止を設定する。
- 上限は各配布回での参加者ごとの累計。昼食の受取によって夕食の受取枠は減らない。分割受取では累計数量を検証する。
- 担当者が配布回を選び、QRまたは名簿で対象者を確認して数量を確定する。入館済みでも未入館でも利用でき、配布によって入場チケットの状態は変わらない。
- 同時処理、再送、上限判定、監査を原子的に扱う。同じ操作IDの再送は同じ結果を返し、異なる内容での再利用は拒否する。管理者は理由付きで取消でき、履歴を保持して受取枠を復元する。
- 組織・イベント・会場担当・QR有効期限・参加者/チケットの失効状態をサーバーで検証する。在館中は現在の在館会場、退館中は登録時の会場を使い、会場が未割当の場合は担当会場を指定する。viewerは閲覧のみ。配布担当者に回答や連絡先を追加開示しない。

## 2. 入退館履歴

- 単発の入場資格受付とは独立して、入館・退館・再入館を記録する。誤受付の取消を退館の代わりにしない。
- イベントと参加者ごとに現在の滞在状態を保持する。入館中の会場は1つとし、別会場への移動は元の会場を退館してから入館する。同時処理・再送による重複遷移を防ぎ、時刻、担当者、会場と履歴を残す。
- 累計受付数と現在の滞在人数を区別する。配布の受取資格は現在の入館状態と独立する。
- 操作時点の状態番号を照合し、古い端末の退館・入館で新しい状態を上書きしない。失敗した遷移は人数に加えず、履歴では不成立として示す。担当会場は各操作で再検証する。
- 入退館をまだ記録していない参加者は「未入館」として扱う。既存の単発受付済みを自動で在館中に変換しない。運用開始時は、実際に滞在している人の入館を職員が記録してから現在人数を使う。
- 在館中の参加者によるチケット取消は先に退館を記録するよう求め、人数だけが消えることを防ぐ。

## 3. 紙のQRカード・世帯管理

- スマホやメールがない人にも、職員が印刷してQRカードを渡せるようにする。カードはイベント内の資格に限定し、QR値に氏名や住所を含めない。
- 通常のカード追加発行では既存QRを維持する。管理者の理由付き紛失再発行は、その参加者のメールQR・紙QRを含む従来の受付QRをすべて失効させる。応答喪失時は同じ操作IDで元の結果を確認し、追加発行や再失効を繰り返さない。
- 参加者の認証用トークンと受付QRが分離された現行チケットでは、紛失再発行で参加者ログインを変更しない。旧形式v1は同じ値を認証にも使うため、漏えいした旧リンクによる認証も無効化する。既存Passkey・参加者セッションは維持し、旧リンクしかない参加者はメールリンクなどで復旧する。
- カードはPNGとして印刷・保存できる。サーバーにはQRの生値を保存せず、応答が途切れた場合の再確認は発行画面に残る操作情報を使う。画面を閉じた後にそのQRを取り戻す機能はないため、新しいカードを追加発行する。
- 同じイベント内の登録者を世帯としてまとめる。1世帯50人まで、1人が所属できる有効な世帯は1つ。代理受取では受取担当と配布対象者を区別し、明示的に選んだ対象者20人までの数量を指定して各人の枠を消費する。受取担当自身も対象者として選べる。個別受取と代理受取の二重配布を防ぐ。
- 代理受取は全対象者分を一括で成立または拒否し、管理者の理由付き取消も一括で扱う。個人1人分だけの取消は受け付けない。上限超過の試行は未配布として履歴へ残す。
- 世帯変更で過去の配布履歴を書き換えない。世帯名や氏名を世帯の識別キーにしない。

## 4. 通信断対応

- 通信可能な間に、担当者が明示的に端末へ運用情報を準備する。同じブラウザーの保存領域に1担当者・組織・イベント・会場の準備情報を保持する。別会場の準備を2タブで開始しても先の準備情報を上書きしない。対象は最大1000人、準備の有効期間は12時間、端末内の記録は最大500操作。静的画面と最小限の担当範囲の名簿を保持し、連絡先やカスタム回答、QRの生値を保存しない。
- 準備対象は現在の在館会場、退館中なら登録時の会場で絞る。未割当の参加者は、担当者が選んだ会場で扱えるよう準備対象に含める。実施中の配布回100回、受付QRは1人32件・全体10000件、配布使用状況30000組までとし、上限を超えた場合は一部だけの名簿を黙って保存せず準備を拒否する。
- 未割当の参加者は複数会場・端末の準備名簿に同時に現れ得る。準備名簿の人数を会場の在館数として合算しない。現場で窓口を決めるか会場を割り当て、同じ人を複数のオフライン窓口で扱わないよう引き継ぐ。
- 通信断中の操作は端末内の未同期記録として扱い、確定済みと表示しない。復旧後は操作IDを維持して再送し、最新の認証・権限・受取上限を再検証する。競合・失効・権限変更を表示し、失敗記録を黙って破棄しない。
- 複数の完全オフライン端末間での即時の二重配布防止は保証しない。現場では窓口/配布回の担当を分け、必要なら紙へ切り替えて復旧後に照合する。
- 同期時に受取上限や在館状態が競合しても、現物の受渡しや人の移動を取り消すものではない。サーバー記録の成立・不成立と、現場で実際に渡した数量・移動を分けて照合する。端末の書出しは確認用のJSONであり、そのファイルを自動で再取込する機能はない。
- オフライン専用画面で準備済みの参加者について個別配布と入退館を記録する。世帯代理受取、未準備の端末、未登録者、新しい配布回の追加、資格の再発行にはオンライン運用または紙の代替を用意する。完全な通信断での新規参加者登録は紙/CSVの後取込から始める。
- 端末の準備解除・ログアウトで個人情報を消去する。保存期限、件数上限、未同期記録の確認・書出し・消去を明示する。
- 期限切れの準備名簿・QR一覧は利用中のタイマーまたは次回起動時の確認で消去する。未同期操作の識別情報は同期・書出しに必要なため残す。別アカウント・組織へ切り替わった場合も氏名を消去し、未同期操作を元の担当者用に保留する。端末の準備解除による操作の破棄は確認を求め、ログアウト前には未同期操作の処理を求める。
- ブラウザーの永続保存を要求しても、ブラウザー設定による削除、保存容量の不足、端末紛失で記録を失う可能性がある。端末保存を唯一の控えにせず、紙や書出しを併用する。未同期記録をCSV取込でそのまま受取履歴へ戻す機能はない。

## 検証

各段階でWorker/D1の実行テスト、型チェック、ブラウザ受入テストと独立レビューを行う。配布回の独立性、並行上限判定、理由取消、旧QR互換、権限境界、世帯代理の対象者ごとの上限、通信断中の再読取・復旧時の再送・競合・端末情報消去を重点確認する。実端末のPasskey・カメラと避難訓練での実運用は自動テストと区別して記録する。

### 配布管理の受入確認

ブラウザで、受付済みQRによる昼食2食の受取、上限超過の拒否、後から追加した夕食の受取、サーバー記録後の応答喪失と原結果照会、理由付き取消と枠の復元を確認した。配布操作後も既存の単発受付状態は維持された。390px幅の画面も確認した。Workerテストでは権限・旧QR互換・原子的な上限判定・監査と取消を検証している。

### 入退館の受入確認

同じ発行済みQRで入館・退館・再入館・退館の後に別会場へ移動し、登録時の会場割当と既存の受付済み状態が維持されることを確認した。現在在館数は0→1→0となり、延べ入館は3件、成立した履歴は更新順に6件、不成立の操作は3件として区別された。応答喪失後の原結果照会と古い状態番号の拒否もブラウザで確認した。

Workerテストでは現在会場の担当範囲、同時状態更新、同一操作の再送、監査失敗時の全体ロールバック、APIトークン、組織・閲覧者の境界、在館中の参加取消拒否を検証した。この段階の全Worker72件・ブラウザ5件が成功し、390px幅で画面を確認した。履歴のUTC時刻も端末の現地時刻に変換して表示する。

### 紙QR・世帯代理受取の受入確認

画面・サーバー応答・印刷ウィンドウに表示したPNGを実際にQRデコードし、同じ受付URLとして読み取れることを確認した。追加発行では元のQRが使え、紛失再発行後は元のメールQRと追加カードQRが拒否された。再発行の応答喪失後も原結果を確認してPNGを再構築でき、再送によって後から発行したカードを再び失効させなかった。現行チケットの参加者認証は維持された。

世帯作成・名簿からのメンバー追加・2人分の代理受取をブラウザで確認した。同じ世帯名でも識別IDは異なる。記録済み対象者と未受取対象者を含む上限超過は全員未配布となり、履歴にも未配布として表示された。代理受取の個人分だけの取消は拒否され、理由付き一括取消で全対象者の枠が戻り、再取消は拒否された。

独立レビューで担当会場変更後の結果閲覧、世帯変更時の非同期応答、履歴の表示形式を修正し、承認を得た。この段階のWorker全78件、ブラウザ5件、型検査が成功した。CSV列対応のブラウザ実行エラーも修正し、受入テストではJavaScript実行エラーがないことを確認している。

### 通信断対応と最終受入確認

通信可能な間に会場を選んで準備し、通信断中に同じQRまたは準備名簿から個別配布・入館・退館を記録した。オフラインで再読み込みしても6件の操作IDと順序が維持された。同じブラウザーの2タブで配布を同時操作しても上限1件を超えず、別会場を同時に準備しても先の会場を上書きしなかった。保存容量不足を模した失敗では操作を保存済みと表示せず、未同期件数も増えなかった。

12時間の期限を進める検証では、準備した氏名とQR照合一覧が消去され、新しい操作は停止した。期限前に記録した未同期操作は保持され、復旧後に元の担当者で同期できた。別利用者のセッションを模した場合も氏名を消去し、元の担当者に戻るまで未同期操作を保留した。

別端末が先に受取枠や在館状態を更新した場合、配布上限・状態番号・後続操作の競合3件を要照合として残した。他の参加者の記録は同期でき、配布の応答喪失後は元の操作IDで結果を照会して二重記録を防いだ。確認用JSONには未同期3件が残り、QRの生値・資格ハッシュは含まれなかった。静的キャッシュにAPI応答や参加者QRがないこと、準備解除とログアウトで保存名簿・操作・確認履歴を消去することも確認した。

独立レビューで準備の競合防止と復旧時のログイン再確認を修正し、承認を得た。最終確認はWorker83件、通常テスト12件、運用テスト4件、ブラウザ5件が成功し、型チェックはエラー・警告0件、Webビルドも成功した。ブラウザのJavaScript実行エラーがないことと390px幅での世帯・オフライン画面を確認した。この変更はまだ本番へ反映していない。

## 現場での運用

1. 平時のイベントや避難所をイベントとして作成し、窓口・避難場所を会場として登録する。担当職員を会場へ割り当てる。避難所で迅速な名簿作成を優先する場合は、必須の申込項目を増やさず氏名だけで当日登録を始める。メールや本人のスマホは必須ではない。
2. スマホがない人には名簿から紙QRカードを発行し、表示された氏名を確認して渡す。QRは入退館と各配布回で共通して使える。紛失が確認された場合は管理者が理由を記入して再発行する。
3. 実際にその場所に滞在している人について「入館」を記録し、移動・外出時は「退館」を記録する。現在人数はこの記録を基準とする。事前登録人数・単発受付数を現在人数として扱わない。
4. 昼食、夕食、翌日の朝食、ノベルティーなど、配る機会ごとに配布回を追加する。各回の単位と1人あたり上限を決め、渡した対象者と数量を確定する。世帯でまとめて渡す場合も全対象者を名簿へ登録し、世帯の受取担当と配布対象者をそれぞれ選ぶ。
5. 配布回や入退館の結果が不明なときは、同じ操作の結果確認を使う。新しい操作を作って渡し直さない。誤記録は管理者が理由付きで取り消し、世帯受取は全対象者分を一括で訂正する。
6. 通信断に備える端末では、通信可能な間に担当会場を明示して準備する。端末の未同期件数を点検し、復旧時に同期する。競合は現場の控えと照合する。端末を引き継ぐ前に、未同期記録の処理・書出しを確認して準備情報を消去する。

この実装の自動テストと、避難訓練での職員・実機・プリンター・通信断を含む運用確認は別に扱う。初回の現場利用前に少人数で受付、カード受渡し、外出・移動、代理受取、通信断からの復旧を一巡する。
